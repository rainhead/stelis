# Toolchain, installation and the container image

Read this before changing how Racket or its packages are installed, CI's setup, the [`Dockerfile`](../../Dockerfile), the image workflow, or a consumer repository's Dockerfile that copies Stelis out of the image.

Toolchain: **Racket v9.3 CS** (on `PATH` at `/Applications/Racket v9.3`). Core is `#lang racket/base` under [`src/`](../../src/); the Datalog planner needs the `datalog` package (`raco pkg install datalog`) and the DASL CIDs need `sha` — unlike `datalog`, it is NOT in the full distribution, so CI installs it explicitly, from the commit [`racket-deps.txt`](../../racket-deps.txt) pins (st-8u3: the catalog's entry follows the package's git branch, so an unpinned install is different code on different days). Every installer, salishsea's Dockerfile included, takes the source from that file — through [`scripts/install-racket.sh`](../../scripts/install-racket.sh) (st-2t1), which installs the pinned minimal build from [`racket-downloads.tsv`](../../racket-downloads.tsv) plus the packages into a prefix, mirror first (`STELIS_DOWNLOAD_MIRROR`), checksum deciding, then converts the catalog packages' machine-independent code to native code, once, at install time ([`scripts/native-code.rkt`](../../scripts/native-code.rkt)), because Racket would otherwise compile that code again on every launch, about 1 s on a Fly Machine (st-3un); CI gets its Racket that way, so no host carries its own copy of the steps. Container hosts get the IMAGE (st-9ov, [ADR 0017](../adr/0017-stelis-ships-as-an-image-per-commit.md)): the image workflow builds the [`Dockerfile`](../../Dockerfile) on every push to main and publishes `ghcr.io/rainhead/stelis:<commit>` — the install script's Racket at `/opt/racket` and the engine compiled at `/opt/stelis`, with the commit written to `/opt/stelis/commit` — and a consumer's Dockerfile copies those two trees by DIGEST ([`scripts/image-digest.sh`](../../scripts/image-digest.sh) resolves the commit's tag and refuses unless the image's revision label is that commit). The suite runs INSIDE the image, as a non-root user on a read-only root, before anything is pushed; that gate is what found the `sha` package's FFI need for libcrypto, which the build stage and every curl-carrying host had by accident. Not in the image, on purpose: the DuckDB CLI (a project's pin, coupled to its DuckDB library) and git (pin `SOURCE_DATE_EPOCH`). No build step — Racket compiles on demand.
